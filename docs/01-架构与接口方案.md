## 1. 直播弹幕接口（已查证）

主要依据：blivedm `blivedm/clients/web.py`、`ws_base.py`（master，2026-08-15），与 PiliPlus `lib/tcp/live.dart`、`lib/http/live.dart`（2026-09-23）和 JLiverTool `crates/jlivertool-core/src/bilibili/api.rs`（2026-09-19）三方交叉比对，用法一致。

| 步骤 | 接口 | 说明 |
|---|---|---|
| ① 获取 buvid3 | `GET https://www.bilibili.com/` 取 Set-Cookie 里的 `buvid3`（blivedm 做法）；或 `GET https://api.bilibili.com/x/frontend/finger/spi` 取 `b_3/b_4`（BiliNest 做法） | 认证包里要带 buvid |
| ② WBI 密钥 | `GET https://api.bilibili.com/x/web-interface/nav` → `data.wbi_img.img_url/sub_url` 文件名拼接，按 32 位置换表取字符 | 未登录也返回 wbi_img；blivedm 缓存 11h59m |
| ③ 真实房间号 | `GET https://api.live.bilibili.com/room/v1/Room/get_info?room_id=短号` → `data.room_id`、`data.uid` | JLiverTool 用 `room/v1/Room/room_init?id=`，两者都可 |
| ④ 弹幕服务器 + token | `GET https://api.live.bilibili.com/xlive/web-room/v1/index/getDanmuInfo?id=房间号&type=0` **＋ WBI 签名**（PiliPlus 额外带 `web_location=444.8`） | 返回 `host_list[]`、`token`；code=-352 表示签名/风控问题，需重取 WBI key |
| ⑤ 连接 | `wss://{host}:{wss_port}/sub`，UA 要与请求 token 时一致（blivedm 注释：“web端的token也会签名UA”） | 多个 host 轮换重试 |
| ⑥ 认证包 | op=7，JSON：`{"uid":0或登录uid,"roomid":真实房号,"protover":3,"platform":"web","type":2,"buvid":"...","key":token}` | 回包 op=8，`code=0` 成功，`-101` token 错误需回到 ④ |
| ⑦ 心跳 | 每 30s 发 op=2 空包；回包 op=3 前 4 字节是人气值（已废弃） | 35s 收不到任何数据判定掉线 |
| ⑧ 业务包 | op=5；`ver=3` 为 **brotli** 压缩，解压后里面是多个子包；`ver=0` 是原始 JSON；`ver=2` zlib（web 端已不用） | 包头 16 字节大端：len(4) headerLen(2) ver(2) op(4) seq(4) |

需要解析的 cmd（按 blivedm 当前的 `_CMD_CALLBACK_DICT`）：

| 内容 | cmd | 格式要点 |
|---|---|---|
| 普通弹幕 | `DANMU_MSG`（cmd 可能带 `:xxx` 后缀，要截掉） | `info[1]`=内容；用户名 `info[2][1]`，新版也在 `info[0][15].user.base.name`；`info[0][15].extra` 是 JSON 字符串 |
| 跨房弹幕 | `DANMU_MSG_MIRROR` | 同上 |
| 醒目留言 | `SUPER_CHAT_MESSAGE` / 删除 `SUPER_CHAT_MESSAGE_DELETE` | `data.price/message/user_info.uname` |
| 礼物 | `SEND_GIFT`，以及 **2026-07 灰度的 `SEND_GIFT_V2`**（`data.pb` 是 base64 的 protobuf） | V2 字段号见 blivedm `models/pb.py` |
| 进场/关注 | `INTERACT_WORD_V2`（`data.pb` base64 protobuf，2025-09 起） | uid=1, uname=2, msg_type=5（1进入 2关注 3分享…） |
| 上舰 | `GUARD_BUY` / `USER_TOAST_MSG_V2` | 可选 |

**未登录的限制（已查证）**：blivedm `sample.py` 当前注释原文：“不填也可以连接，但是收到弹幕的**用户名会打码，UID会变成0**”。
**未查到的**：未登录时弹幕**数量**是否会被限制/抽样，我没找到任何证据，不下结论。

## 2. 视频弹幕接口（已查证）

主要依据：BiliNest `server.mjs`（2026-09-23 发布 1.4.9，专门修过弹幕解码）＋ PiliPlus 的 protobuf 定义（字段号两者一致）＋ yt-dlp `extractor/bilibili.py`（2026-09-16）。

| 用途 | 接口 | 说明 |
|---|---|---|
| 视频信息/分P | `GET https://api.bilibili.com/x/web-interface/view?bvid=`（BiliNest 走 WBI 版 `/x/web-interface/wbi/view`） | `data.pages[]` 里有 `cid`、`part`、`duration` |
| 只要分P | `GET https://api.bilibili.com/x/player/pagelist?bvid=` | 无需签名（yt-dlp、PiliPlus 都在用） |
| **弹幕分段（主）** | `GET https://api.bilibili.com/x/v2/dm/wbi/web/seg.so?type=1&oid={cid}&segment_index={1..}` ＋ WBI 签名；失败回退无签名 `/x/v2/dm/web/seg.so` | 每段 6 分钟；返回 protobuf `DmSegMobileReply`；**HTTP 304 = 该段无弹幕** |
| 弹幕 XML（备用） | `https://api.bilibili.com/x/v1/dm/list.so?oid={cid}` 或 `https://comment.bilibili.com/{cid}.xml` | 只有“实时弹幕池”，比分段少 |
| 请求头 | `Referer: https://www.bilibili.com/`、浏览器 UA、Cookie 带 buvid3/buvid4 | BiliNest 做法 |

`DanmakuElem` 字段号：id=1, progress=2(毫秒), mode=3, fontsize=4, color=5, midHash=6, content=7, ctime=8, weight=9, pool=11, idStr=12, attr=13。

几件必须说清楚的事：
1. **视频弹幕里没有用户名**，只有 `midHash`（发送者 UID 的 CRC32）。所以视频模式下“显示用户名”做不到；“按用户屏蔽”只能是“长按某条弹幕 → 屏蔽这个发送者（按 hash）”。我不会做 hash 反查 UID。
2. **“全部弹幕”做不到字面意义上的全部**。分段接口返回的是当前弹幕池（受视频弹幕上限约束，BiliNest 笔记写“每段最多 6000 条”，这条我只在它的笔记里看到，未独立核实）。更早被挤出池子的“历史弹幕”接口我**没能查证**当前用法，不纳入计划。
3. 每个视频按时长 ÷ 6 分钟请求 N 段，我会串行、间隔 300ms 左右请求，避免触发 412 风控。

## 3. 扫码登录（已查证，但有一个同机扫码问题）

依据：JLiverTool `api.rs` 与 BiliNest `server.mjs`，两者一致。

- 生成：`GET https://passport.bilibili.com/x/passport-login/web/qrcode/generate` → `data.url`（做成二维码）、`data.qrcode_key`
- 轮询：`GET https://passport.bilibili.com/x/passport-login/web/qrcode/poll?qrcode_key=` → **看 `data.code`**：`0` 成功 / `86101` 未扫 / `86090` 已扫待确认 / `86038` 过期
- 成功后从 **Set-Cookie** 取 `SESSDATA、bili_jct、DedeUserID、DedeUserID__ckMd5、sid`（若没带，BiliNest 会再请求一次 `data.url` 补取）
- 退出：`POST https://passport.bilibili.com/login/exit/v2`，表单 `biliCSRF=bili_jct`
- 本地存储：用 Android Keystore 生成 AES-GCM 密钥加密后存 DataStore。**不用** `EncryptedSharedPreferences`（androidx security-crypto 已被官方弃用）。

**问题**：二维码显示在这台手机上，而扫码要用这台手机上的 B 站 App。可选办法（都**未实测**）：
- A. 把二维码存到相册 → B 站 App“扫一扫”里从相册选图。B 站 App 扫一扫是否支持相册识别，我没有证据，需要你试一下。
- B. 在另一台设备（电脑/平板）上显示二维码，用手机扫。
- C. 兜底：手动粘贴浏览器里的 SESSDATA（不输入账号密码，符合你的要求）。

## 4. 视频进度同步：三个方案对比

本应用读不到官方 App 播放器的内部状态，这点确认无误。对比如下：

| | a) 手动同步 | b) 自带播放器 | c) 读系统媒体会话（MediaSession） |
|---|---|---|---|
| 原理 | 悬浮窗里有 播放/暂停、进度条、±1s/±5s，本地时钟推进 | 本应用内用 Media3/ExoPlayer 播放 B 站视频流（`/x/player/wbi/playurl`，DASH，需 Referer） | 用户授予“通知使用权”后，`MediaSessionManager.getActiveSessions()` 能拿到其他 App 发布的播放状态：位置、速度、暂停/播放、标题 |
| 精度 | 取决于手动对齐，暂停/拖动后要重新对 | 精确到帧 | 如果 B 站 App 发布了会话，精度应在 1 秒内，且能自动跟随暂停/拖动/倍速 |
| 稳定性 | 最稳，不依赖任何接口 | 依赖 playurl 接口（WBI、风控、画质限制，未登录画质受限） | **完全取决于 B 站 App 是否发布 MediaSession、是否持续更新进度——我查不到任何资料证明它会，这是最大的未知** |
| 风险 | 无 | 最高：就不再是“用官方 App 看”了；律师函明确点名“抓取付费内容”，播放流接口比弹幕接口敏感得多；开发量最大 | 低：只用 Android 公开 API，不碰 B 站接口 |
| 能否自动识别是哪个视频 | 否 | 是 | 可能（如果会话里带标题，可拿标题去匹配） |

其他我考虑过、**不推荐**的方案：
- 无障碍服务读取播放器上的时间文字：只有控制栏显示时才有文字，B 站播放器是否把它暴露给无障碍树未知，版本一更新就可能失效，而且无障碍权限很敏感。
- 录屏 + OCR 识别进度：耗电、需要控制栏常显，不现实。

**我的推荐：a + c 组合**
1. 先做**手动同步**（保底，一定能用）。
2. 在第一步交付的悬浮窗框架里，**顺带放一个“媒体会话探针”页面**：你授权通知使用权后，在 B 站 App 里播放视频，探针实时显示系统里有哪些媒体会话、位置是否在走、暂停/拖动后是否变化。花你 5 分钟就能确定 c 是否可行。
3. 如果探针证明可行，就做“自动同步 + ±N 秒微调”；不可行就只保留手动。
4. b 不建议做；如果你坚持要，放到最后单独评估。

## 5. 整体架构

```
app/
├─ data/bili/                ← 接口层：唯一接触 B 站协议的地方，接口变了只改这里
│  ├─ http/     BiliHttpClient（OkHttp，统一 UA/Referer/CookieJar/412 退避）
│  ├─ auth/     WbiSigner、BuvidProvider、QrLoginApi、CredentialStore（Keystore 加密）
│  ├─ live/     LiveRoomApi（房号/getDanmuInfo）、LivePacketCodec（包头/brotli）、
│  │            LiveWsClient（OkHttp WebSocket）、LiveCmdParser（cmd → 统一模型）
│  ├─ video/    VideoApi（view/pagelist）、DmSegApi（seg.so）、DmProtoDecoder（手写 protobuf 解码）
│  └─ link/     LinkResolver（直播间链接、BV/av、b23.tv 短链跳转解析）
├─ domain/                    ← 与 B 站无关的业务逻辑
│  ├─ model/    DanmakuItem（kind=弹幕/SC/礼物/进场/系统, text, uname?, uid?, midHash?, color, time, progressMs?）
│  ├─ live/     LiveSession（状态机：连接中/已连接/重连中/错误；指数退避；网络切换强制重连）
│  ├─ video/    VideoTimeline（按 progress 排序 + 二分查找）、PlaybackClock 接口
│  │            ├ ManualClock（手动）  ├ MediaSessionClock（方案 c，待探针验证）
│  ├─ filter/   FilterEngine（关键词/正则/用户/白名单模式/重复合并 ×N）
│  └─ buffer/   DanmakuBuffer（上限 N 条，每 150ms 批量推给 UI）
├─ service/   OverlayService（LifecycleService + 前台服务 specialUse + 通知 + NetworkCallback）
├─ overlay/   FloatingWindowController（WindowManager：拖动/缩放/锁定穿透/折叠小图标）
│             DanmakuListView（RecyclerView，“回到最新”按钮）
└─ ui/        Compose 界面：首页输入、分享接收、设置、过滤规则、登录、权限与保活引导、探针
```

数据流：`WebSocket 线程 → 解析(Default) → 过滤 → DanmakuBuffer → 每 150ms 一批 → 主线程 RecyclerView.notifyItemRangeInserted`；列表超过上限（默认 300 条，可调）从头部删除。

### UI 技术选型（建议）
- **悬浮窗用 View（RecyclerView）**，设置等普通界面用 **Compose**。
- 理由：悬浮窗挂在 `WindowManager` 上，不在 Activity 里。Compose 放进悬浮窗需要自己给 `ComposeView` 提供 `LifecycleOwner`、`SavedStateRegistryOwner`、`ViewModelStoreOwner`（让 Service 继承 `LifecycleService` 并实现 `SavedStateRegistryOwner`，在 `onCreate/onDestroy` 驱动生命周期）。可以做，但拖动/缩放/触摸穿透这类窗口级操作用 View 更直接，高频追加列表 RecyclerView 也更可控。
- 如果你更想全 Compose，我会用上面说的 Lifecycle 方案，也没问题。

### 悬浮窗关键点
- `TYPE_APPLICATION_OVERLAY`，默认 `FLAG_NOT_FOCUSABLE | FLAG_LAYOUT_NO_LIMITS`，在全屏视频上方也能显示。
- **锁定（触摸穿透）**：加 `FLAG_NOT_TOUCHABLE`。**Android 12+ 的限制（已查证官方文档）**：穿透触摸的悬浮窗整体不透明度必须 ≤ 0.8，否则下层 App 收不到触摸。所以锁定时窗口 `alpha` 会被自动压到 ≤ 0.8。
- 解锁入口：锁定后窗口收不到触摸，所以解锁放在**前台通知的按钮**上（加上折叠后的小图标）。
- 回到最新：用户向上滑动即暂停自动滚动，出现“回到最新 (n 条新)”按钮。

### 前台服务与权限（已查证官方文档）
- 前台服务类型用 **`specialUse`**（要声明 `FOREGROUND_SERVICE_SPECIAL_USE` 和 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`）。**不用 `dataSync`**：Android 15 起 dataSync 每 24 小时只允许后台运行合计 6 小时，看长直播会被系统掐掉。
- Android 13+ 运行时申请 `POST_NOTIFICATIONS`；用户拒绝时服务仍能运行，只是通知不显示在通知栏。
- 最低 Android 8.0（API 26）。

### 国产 ROM 保活与权限（做成应用内引导页）
各家设置路径随系统版本变化，不同版本位置不同，我会在引导页里优先跳到“应用详情页”，再用文字说明，不硬编码厂商的内部 Activity（那些经常失效）：
- 通用：悬浮窗权限、忽略电池优化（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）、在最近任务里锁定本应用。
- MIUI/HyperOS：显示悬浮窗、自启动、省电策略设为“无限制”。
- ColorOS：应用耗电管理里允许后台运行/完全后台行为、自启动。
- HarmonyOS：应用启动管理改为手动管理，打开自启动/关联启动/后台活动。
- 具体菜单名我没有逐个机型核实，引导页文案会写成“大致位置”，你用哪家手机我可以按你的实机再调整。

### 依赖（版本号在你那边编译时再确认，我这里连不上 Maven）
OkHttp（HTTP + WebSocket）、kotlinx-coroutines、kotlinx-serialization-json、`org.brotli:dec`（Google 的纯 Java brotli 解码器）、DataStore、RecyclerView、Compose BOM、ZXing core（生成二维码）。protobuf 用手写解码器（只解几个字段，不引入 protobuf 插件）。

## 7. 我不确定、需要你知道的点（汇总）

1. 所有接口**没有实际请求验证**（我的环境连不上 B 站），只保证与当前活跃项目一致。
2. 未登录时直播弹幕**数量**有没有限制：没找到证据。
3. 未登录时 `getDanmuInfo` 被风控（-352）的概率、以及不带 token 连默认服务器现在还能不能收到弹幕（blivedm 保留了这个降级路径）：未知。
4. B 站 App 是否发布 MediaSession 并更新进度：未知，靠探针验证。
5. 同一台手机上扫码登录的可行方式：未实测。
6. `b23.tv` 短链：按常规 HTTP 302 跳转解析，未实测。
7. 视频“历史弹幕”接口：未查证，不纳入。
8. 我这边**无法编译**，代码需要你在 Android Studio 里编译；编译报错把错误贴给我即可。
